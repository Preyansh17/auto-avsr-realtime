**Week:** 2026-07-07 → 2026-07-13
**Branch:** `realtime-port`
**Focus:** Resolve the streaming Whisper investigation left blocked on 2026-07-09, instrument real perceived latency (TTFT / word-commit lag) for both Whisper and Nemotron so streaming numbers are comparable on more than just WER, and re-run the whole Whisper pipeline against a newly audited three-domain (legal/legacy/merged) split with 3 seeds each — the first time legacy has ever had an honest train/val/test evaluation in this project.

## TL;DR

- **Streaming Whisper resolved.** The 2026-07-09 "garbage output" mystery (`"Good night, Jason."` instead of the reference transcript) was a silently **fp16-corrupted checkpoint conversion** — the `.pt` file's weights didn't bit-match the source HF model, and the ~0.002 weight-diff that looked like benign bf16 training noise was actually the corruption itself. Reconverting bit-exact fixed everything end to end: offline decode correct, full SimulStreaming run emits the exact reference transcript incrementally.
- **New hard rule going forward: every checkpoint format conversion must assert bit-exactness (max diff == 0.0) against the source state dict before it's trusted**, plus an end-to-end decode of a known clip. All conversion scripts this week (`convert_splitv1_all.py`, the earlier `reconvert_and_test.py`) enforce this and abort/delete the output file on failure rather than silently continuing.
- Built real perceived-latency metrics for streaming Whisper — **TTFT** (stream start → first text visible) and **word-commit lag** (word finished being spoken → its text visible), both computed in *simulated real time* (a chunk's audio only "exists" at `(k+1)×segment` seconds, matching a live deployment, not the eval loop's instant feed rate).
- Swept segment length (1.2s/0.6s/0.3s) and AlignAtt's `frame_threshold` (25/18/12) looking for a lower-latency operating point. **Neither knob gets Whisper meaningfully below a ~1.4-1.6s word-lag floor** — segments shorter than 0.6s cost WER for almost no latency gain, and halving `frame_threshold` only shaved ~0.15-0.2s off every emission. The floor looks structural (decode/context latency intrinsic to AlignAtt-wrapped Whisper), not a search problem. **0.6s segments is the practical sweet spot**: ~1.5s word lag, single-digit-to-teens WER depending on domain.
- Gave Nemotron the same latency instrumentation and found a **real README bug**: the existing "Nemotron streaming 33.3%/31.7%" leaderboard row was actually **offline** WER (the sbatch that produced it calls `nemotron_eval.py`, not `nemotron_streaming_eval.py`) — true cache-aware streaming numbers for Nemotron on the honest splits had never been run. Ran them: **WER penalty is near-zero (+0 to +0.44pp)** since Nemotron's encoder is causal by construction, but **TTFT (2.2-4.4s) is comparable to or worse than Whisper's**, despite ~10x lower per-chunk compute — its native chunk size dominates over compute speed. Swept Nemotron's chunk-size knob (`att_context_size`, 4 discrete presets down to fully causal) and found it barely moves TTFT (~1s at most) while WER degrades sharply — not a useful lever either.
- Hit a real, reproducible **NeMo library bug**: `compute_timestamps=True` crashes cache-aware streaming's carried decode state on both of NeMo's greedy RNNT decode paths (two different exact tracebacks, confirmed independently) — Nemotron word-commit lag is unavailable until NeMo fixes this.
- Re-ran the full Whisper large-v3+SpecAugment pipeline (offline + streaming, 3 seeds) against a **newly, independently audited three-way split** (`split_audit.json`, sha256-tracked sources) covering all three domains for the first time — **legacy's first-ever honest numbers**. Two real bugs hit along the way, one a red herring: SLURM's `QOSMaxGRESPerUser` reason looked like a resource cap but the actual crash was a **token-vocabulary mismatch** (the new split's labels were still in the old unigram5000 tokenization, not this pipeline's spm_unigram_1023) — fixed by regenerating all 9 label files.
- **Legacy's variance is real and gets worse under streaming, with the seed ranking flipping entirely**: offline range 17.5-40.0% (22.5pp), streaming range 22.5-50.0% (27.5pp) — and the *best* offline seed becomes the *worst* streaming seed. Legal and merged stay comparatively tight.
- Verified the new split has **zero train/val/test overlap** in all three domains, and separately confirmed its merged test set is a genuinely different (only 3/40 clips shared), individually-clean benchmark from the old ad-hoc merged split — not a leak, just two different valid partitions of a mostly-overlapping clip pool, which is most of why the new merged offline WER (8.22% mean) reads so much higher than the old single-seed headline (2.64%).
- Ran `/doctor` on the Claude Code setup itself: found `claude-mem`'s memory-capture hooks had been firing on every tool call all month and failing 100% of the time (missing the Bun JS runtime); fixed by installing Bun and adding its PATH export to `~/.zshenv` (not just `~/.zshrc`, which non-interactive login shells — how the hook resolves PATH — never source).

## What we did

### 1. Streaming Whisper root cause — a corrupted checkpoint, not SimulStreaming

Session picked back up from the 2026-07-09 handoff (option 1: keep digging). Decisive three-way test: (A) HF `generate()` in the deployment env decoded correctly, (B) stock openai-whisper's offline `decode()` with the *converted* checkpoint reproduced the exact same garbage as the streaming runs — proving SimulStreaming itself was never the problem. (C) A full state-dict comparison between the HF-loaded weights and the converted `.pt` looked "close" (max diff 0.0019) but should have been **exactly 0.0**, since the converter just renames tensors from the same load — the file was checked and found to be **3.09GB pure fp16**, not the "6.17GB fp32" it was recorded as. A layer-by-layer encoder trace confirmed small per-layer noise compounding into a catastrophic divergence by block 20 (large-v3's known outlier-channel layers), explaining the decoder's degenerate near-immediate-`<|endoftext|>` behavior. Fresh reconversion (verified bit-exact, fp32) fixed everything: correct offline decode, and a full SimulStreaming run emitting `" do you"` → `" know what they think"` → `" think"` — the exact reference transcript, incrementally.

### 2. TTFT and word-commit-lag metrics, in simulated real time

`whisper_streaming_eval.py` gained two new metrics, both computed as if the audio were arriving live: a chunk `k`'s audio only "exists" at `(k+1)×segment_length` seconds, so text derived from it can't be counted as available any earlier than that plus its actual compute time — the eval loop itself feeds chunks instantly, so this had to be modeled explicitly rather than just timing wall clock. **TTFT** = stream start → first non-empty text. **Word-commit lag** = each word's own spoken-end timestamp (from SimulStreaming's AlignAtt attention-frame alignment) → the wall time its text became visible. Report includes mean/p50/p95 for both.

### 3. Segment-length and `frame_threshold` sweeps — a latency floor, not a search problem

Swept segment length 1.2s/0.6s/0.3s and `frame_threshold` 25/18/12 (at 0.6s) looking for a genuinely low-latency operating point suitable for live use ("a person says something and the output comes out"). Neither knob delivers: word lag bottoms out around 1.35-1.5s regardless, while WER climbs steadily as either knob is pushed lower. The AlignAtt hold-back (`frame_threshold=25` ≈ 0.5s) accounts for only part of the floor — halving it to 12 frames only bought ~0.15-0.2s, meaning most of the remaining lag is intrinsic to how much committed context the decoder needs before it will emit at all. **0.6s segments, default `frame_threshold=25`** is the practical recommendation; getting meaningfully under ~1s would need a genuinely causal retrain (CarelessWhisper/WhisperRT, still not attempted) rather than more parameter search.

### 4. Nemotron gets the same latency treatment — and a real README bug found

Asked "what's Nemotron's equivalent latency" and discovered the existing leaderboard's "Nemotron streaming 33.3%/31.7%" row was mislabeled: traced the sbatch that produced those exact numbers and confirmed it calls the **offline** `nemotron_eval.py`, not `nemotron_streaming_eval.py` — true streaming Nemotron on the honest splits had never actually been run. Built `nemotron_streaming_eval_latency.py` (same TTFT-in-simulated-real-time approach as Whisper's), using `streaming_buffer.buffer_idx / streams_length × manifest_duration` to get audio-consumed-so-far without needing any hardcoded frame-stride constant. Ran it: **near-zero streaming WER penalty** (Nemotron's FastConformer encoder is causal/cache-aware by construction, unlike Whisper's bidirectional one — there's little "peek at the future" advantage to lose), but **TTFT (2.2-4.4s) is comparable to or worse than Whisper's** despite Nemotron's per-chunk compute being ~10x cheaper (19-26ms vs 170-217ms) — its native chunk size (`chunk_size=[105,112]` encoder frames, ≈1.1s of audio) makes algorithmic latency dominate over raw speed.

Word-level timestamps were attempted (to get Nemotron word-commit lag matching Whisper's) via `model.change_decoding_strategy(compute_timestamps=True)` — hit a genuine NeMo bug on **both** greedy RNNT decode paths: `loop_labels=True` crashes in `hyp.merge_()` (`hyp.timestamp` is a dict, code calls `.extend()` on it); `loop_labels=False` explicitly raises `NotImplementedError("partial_hypotheses support is not supported")`. Confirmed independently with two different jobs/tracebacks — not fixable from the eval script. Nemotron word-commit lag stays unavailable pending an upstream NeMo fix.

### 5. Nemotron chunk-size sweep — not a useful lever either

Followed up "reduce the chunk size" for Nemotron. The obvious `chunk_size`/`shift_size` args don't work directly on this model (`TypeError` in NeMo's own `setup_streaming_params` without both set) — the real lever is `att_context_size`, a small set of **discrete pretrained presets** (`model.encoder.att_context_size_all`: `[[70,13],[70,6],[70,1],[70,0]]`, mapping to ~1.12s/0.56s/0.16s/0.08s chunks respectively). Swept all four on both test sets: shrinking the chunk 14x moved TTFT p50 by **at most ~1s** while WER degraded sharply and monotonically (32-33% → 44-47% at fully causal). Conclusion: Nemotron's TTFT floor is set by something else — most likely the RNNT decoder's own symbol-by-symbol context needs — not the encoder's lookahead window, so this knob doesn't touch the real bottleneck. The pretrained default (`[70,13]`) is already close to the best tradeoff available.

### 6. Audited 3-domain, 3-seed Whisper re-run — legacy's first honest numbers

New data root (`/scratch/th3482/LipVideoData/patient_legal298_legacy96_split_v1`) is an independently audited three-way split — `split_audit.json` documents the exact algorithm and sha256s the source files per domain: legal 238/30/30, legacy 76/10/10 (**legacy's first-ever honest train/val/test split in this project** — previously untested with real held-out data), merged 314/40/40 (ordered legal+legacy union). Launched 9 full-FT Whisper large-v3+SpecAugment finetune runs (3 domains × 3 seeds, standalone sbatch that skips the usual merge-symlink logic since `split_v1` is already pre-split per domain).

Two real operational issues, one a genuine bug:
- **Account switch mid-run**: switched submission from `torch_pr_39_tandon_advanced` to `torch_pr_39_general` mid-session (both congested at different points this week — this preference is now tracked as switchable, not fixed).
- **Real bug**: 4 of the 9 jobs failed within ~1 minute of a resubmit; SLURM's `sacct` reported `QOSMaxGRESPerUser` as the reason, reading like a per-user GPU cap — but `sacctmgr show qos` confirmed no such cap exists for this account's QOS. The actual cause, found by reading the job's own log instead of trusting `sacct`'s reason column: `IndexError: Out of range: piece id is out of range` from `sentencepiece`. The new split's label CSVs have the same 4-column shape as this pipeline's already-regenerated `*_spm1023.csv` files, so they were assumed to already be in the current tokenization — they weren't. Confirmed `spm_unigram_1023.model` has `vocab_size=1023` but the new split's `token_ids` go up to ~5037, the old **unigram5000** vocabulary. Fixed by running all 9 files through `scripts/regenerate_patient_labels.py` (decode via `unigram5000_units.txt`, re-encode with the 1023-piece model), spot-checked the decoded text against the known reference clip before resubmitting, zero rows skipped across all 9 files.

Resubmitted clean, all 9 finetune runs completed, all 9 checkpoints converted to OpenAI format and verified bit-exact (per the new hard rule from §1), and all 9 streaming-evaluated at 0.6s segments (the established sweet spot from §3).

### 7. Legacy's variance is real, and worse under streaming than offline

Legacy's offline WER already showed a 22.5pp range across 3 seeds (17.5-40.0%) — expected given only 10 test clips, but this is the first time it's been measured at all. Streaming didn't average that out; it **widened it to 27.5pp (22.5-50.0%)**, and the seed ranking flipped entirely: the seed that was *best* offline (seed3, 25.0%) became the *worst* under streaming (50.0%). A single-seed streaming number on this domain would have been close to meaningless in either direction — the concrete failure mode 3-seed evaluation exists to catch. Legal (5.46pp streaming range) and merged (1.35pp) stayed comparatively tight. Streaming penalty was fairly consistent across all three domains (+6.7 to +8.8pp mean-to-mean), in the same range as the original legal/merged-only investigation.

### 8. Why the new merged numbers look so different from the old ones — checked, not guessed

The new split's merged offline mean (8.22%) reads much higher than the old single-checkpoint headline (2.64%) — investigated directly rather than assumed. Confirmed: (a) the old split's own train/test had **zero internal overlap** (not leaked), and (b) the new split_v1's own train/val/test also has **zero overlap in all three domains** (checked directly). But the old and new merged *test* sets are **almost entirely different clips** — only 3 of 40 shared — despite matching domain composition (30 legal + 10 legacy either way) and even matching row counts. **27 of the new split's 40 test clips were part of the old split's train314.** Neither split leaked internally; they're just two different, individually-clean partitions of a mostly-overlapping clip pool — like two different exams from the same question bank. The old 2.64% number was a legitimate held-out eval on its own test set; it simply never faced the harder clips the new split happens to hold out. Also explains part of the earlier-noticed "huge difference" in streaming Whisper's headline vs. this week's split_v1 numbers, compounded with §3's segment-length confound (old headline was measured at 1.2s, new at 0.6s — a real, separate effect).

### 9. `/doctor` — a month of silently-failing background hooks, fixed

Ran a full `/doctor` health check on the Claude Code setup itself (unrelated to the ASR work, but real). Found `claude-mem`'s `PostToolUse`/`Stop` hooks had fired on essentially every tool call across the last month of sessions (11,000+ recorded hook events) and **failed 100% of the time**, silently (non-blocking errors never surface to the user) — root cause: the Bun JS runtime the hook shells out to wasn't resolvable. Installed Bun, then found the installer's own PATH fix (appended to `~/.zshrc`) doesn't actually fix the hook, because the hook resolves PATH via `$SHELL -lc` (a non-interactive login shell), and zsh only sources `.zshrc` for *interactive* shells — added the same export to `~/.zshenv` (sourced by every zsh invocation) and confirmed the hook's own exact failing command now runs clean.
