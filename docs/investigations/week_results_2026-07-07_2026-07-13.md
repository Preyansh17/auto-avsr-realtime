## What we did

### 1. Streaming Whisper root cause — a corrupted checkpoint, not SimulStreaming

Session picked back up from the 2026-07-09 handoff (option 1: keep digging). Decisive three-way test: (A) HF `generate()` in the deployment env decoded correctly, (B) stock openai-whisper's offline `decode()` with the *converted* checkpoint reproduced the exact same garbage as the streaming runs — proving SimulStreaming itself was never the problem. (C) A full state-dict comparison between the HF-loaded weights and the converted `.pt` looked "close" (max diff 0.0019) but should have been **exactly 0.0**, since the converter just renames tensors from the same load — the file was checked and found to be **3.09GB pure fp16**, not the "6.17GB fp32" it was recorded as. A layer-by-layer encoder trace confirmed small per-layer noise compounding into a catastrophic divergence by block 20 (large-v3's known outlier-channel layers), explaining the decoder's degenerate near-immediate-`<|endoftext|>` behavior. Fresh reconversion (verified bit-exact, fp32) fixed everything: correct offline decode, and a full SimulStreaming run emitting `" do you"` → `" know what they think"` → `" think"` — the exact reference transcript, incrementally.

### 2. TTFT and word-commit-lag metrics, in simulated real time

`whisper_streaming_eval.py` gained two new metrics, both computed as if the audio were arriving live: a chunk `k`'s audio only "exists" at `(k+1)×segment_length` seconds, so text derived from it can't be counted as available any earlier than that plus its actual compute time — the eval loop itself feeds chunks instantly, so this had to be modeled explicitly rather than just timing wall clock. **TTFT** = stream start → first non-empty text. **Word-commit lag** = each word's own spoken-end timestamp (from SimulStreaming's AlignAtt attention-frame alignment) → the wall time its text became visible. Report includes mean/p50/p95 for both.

### 3. Segment-length and `frame_threshold` sweeps — a latency floor, not a search problem

Swept segment length 1.2s/0.6s/0.3s and `frame_threshold` 25/18/12 (at 0.6s) looking for a genuinely low-latency operating point suitable for live use ("a person says something and the output comes out"). Neither knob delivers: word lag bottoms out around 1.35-1.5s regardless, while WER climbs steadily as either knob is pushed lower. The AlignAtt hold-back (`frame_threshold=25` ≈ 0.5s) accounts for only part of the floor — halving it to 12 frames only bought ~0.15-0.2s, meaning most of the remaining lag is intrinsic to how much committed context the decoder needs before it will emit at all. **0.6s segments, default `frame_threshold=25`** is the practical recommendation; getting meaningfully under ~1s would need a genuinely causal retrain (CarelessWhisper/WhisperRT, still not attempted) rather than more parameter search.

### 4. Nemotron gets the same latency treatment — and a real README bug found

Asked "what's Nemotron's equivalent latency" and discovered the existing leaderboard's "Nemotron streaming 33.3%/31.7%" row was mislabeled: traced the sbatch that produced those exact numbers and confirmed it calls the **offline** `nemotron_eval.py`, not `nemotron_streaming_eval.py` — true streaming Nemotron on the honest splits had never actually been run. Built `nemotron_streaming_eval_latency.py` (same TTFT-in-simulated-real-time approach as Whisper's), using `streaming_buffer.buffer_idx / streams_length × manifest_duration` to get audio-consumed-so-far without needing any hardcoded frame-stride constant. Ran it: **near-zero streaming WER penalty** (Nemotron's FastConformer encoder is causal/cache-aware by construction, unlike Whisper's bidirectional one — there's little "peek at the future" advantage to lose), but **TTFT (2.2-4.4s) is comparable to or worse than Whisper's** despite Nemotron's per-chunk compute being ~10x cheaper (19-26ms vs 170-217ms) — its native chunk size (`chunk_size=[105,112]` encoder frames, ≈1.1s of audio) makes algorithmic latency dominate over raw speed.

Word-level timestamps were attempted (to get Nemotron word-commit lag matching Whisper's) via `model.change_decoding_strategy(compute_timestamps=True)` — hit a genuine NeMo bug on **both** greedy RNNT decode paths: `loop_labels=True` crashes in `hyp.merge_()` (`hyp.timestamp` is a dict, code calls `.extend()` on it); `loop_labels=False` explicitly raises `NotImplementedError("partial_hypotheses support is not supported")`. Confirmed independently with two different jobs/tracebacks — not fixable from the eval script. Nemotron word-commit lag stays unavailable pending an upstream NeMo fix.

### 5. Nemotron chunk-size sweep — not a useful lever either

Followed up "reduce the chunk size" for Nemotron. The obvious `chunk_size`/`shift_size` args don't work directly on this model (`TypeError` in NeMo's own `setup_streaming_params` without both set) — the real lever is `att_context_size`, a small set of **discrete pretrained presets** (`model.encoder.att_context_size_all`: `[[70,13],[70,6],[70,1],[70,0]]`, mapping to ~1.12s/0.56s/0.16s/0.08s chunks respectively). Swept all four on both test sets: shrinking the chunk 14x moved TTFT p50 by **at most ~1s** while WER degraded sharply and monotonically (32-33% → 44-47% at fully causal). Conclusion: Nemotron's TTFT floor is set by something else — most likely the RNNT decoder's own symbol-by-symbol context needs — not the encoder's lookahead window, so this knob doesn't touch the real bottleneck. The pretrained default (`[70,13]`) is already close to the best tradeoff available.

### 7. Legacy's variance is real, and worse under streaming than offline

Legacy's offline WER already showed a 22.5pp range across 3 seeds (17.5-40.0%) — expected given only 10 test clips, but this is the first time it's been measured at all. Streaming didn't average that out; it **widened it to 27.5pp (22.5-50.0%)**, and the seed ranking flipped entirely: the seed that was *best* offline (seed3, 25.0%) became the *worst* under streaming (50.0%). A single-seed streaming number on this domain would have been close to meaningless in either direction — the concrete failure mode 3-seed evaluation exists to catch. Legal (5.46pp streaming range) and merged (1.35pp) stayed comparatively tight. Streaming penalty was fairly consistent across all three domains (+6.7 to +8.8pp mean-to-mean), in the same range as the original legal/merged-only investigation.

### 8. Why the new merged numbers look so different from the old ones — checked, not guessed

The new split's merged offline mean (8.22%) reads much higher than the old single-checkpoint headline (2.64%) — investigated directly rather than assumed. Confirmed: (a) the old split's own train/test had **zero internal overlap** (not leaked), and (b) the new split_v1's own train/val/test also has **zero overlap in all three domains** (checked directly). But the old and new merged *test* sets are **almost entirely different clips** — only 3 of 40 shared — despite matching domain composition (30 legal + 10 legacy either way) and even matching row counts. **27 of the new split's 40 test clips were part of the old split's train314.** Neither split leaked internally; they're just two different, individually-clean partitions of a mostly-overlapping clip pool — like two different exams from the same question bank. The old 2.64% number was a legitimate held-out eval on its own test set; it simply never faced the harder clips the new split happens to hold out. Also explains part of the earlier-noticed "huge difference" in streaming Whisper's headline vs. this week's split_v1 numbers, compounded with §3's segment-length confound (old headline was measured at 1.2s, new at 0.6s — a real, separate effect).

Went one level deeper on a follow-up question (why doesn't merged's 8.22% look like a weighted blend of legal's 7.65% and legacy's 27.5%?). Split each merged checkpoint's `val_hyps.tsv` by domain and computed real WER on each portion separately — first attempt matched `"legacy"` as a path substring and silently classified **every** row as legacy, because the split's own root directory is named `patient_legal298_legacy96_split_v1` (contains "legacy" regardless of which per-clip subdirectory a row is actually in); fixed by matching the exact `/patient_retinaface_legacy/` path segment instead. Real per-domain breakdown, merged-trained model:

| Seed | Legal portion (183 words) | Legacy portion (40 words) | Pooled (= reported merged WER) |
| --- | --- | --- | --- |
| 1 | 6.56% | 25.00% | 9.87% |
| 2 | 6.56% | 12.50% | 7.62% |
| 3 | 4.92% | 17.50% | 7.17% |

Two real findings, not just an accounting explanation: **merged training improves legacy's own WER** (12.5-25.0% inside the merged model vs. legacy-only-trained's 17.5-40.0% — more total data helps a data-starved domain even as a training-set minority), **and it improves legal's too** (4.92-6.56% inside the merged model vs. legal-only-trained's 6.56-8.74%). Pooled WER also weights by word count, not clip count — legacy is only 18% of the merged test set's word mass (40/223 words), capping how much it can pull the pooled number up regardless of its own WER. Merged's number isn't a blend of two independent specialists; it's one jointly-trained model that outperforms both standalone specialists on their own domains. Full 40-clip ground-truth/prediction/domain breakdown (seed1 checkpoint) saved to `results/splitv1_merged_seed1_test40_breakdown.csv` (kept out of git — see §11, real patient utterances).

### 11. Public-repo safety: patient transcript data caught before it reached GitHub

While pushing this week's accumulated local commits (`git push`), Claude Code's own safety classifier blocked it: the repo is **public**, and the outgoing history contained real patient speech transcripts in two places — a new per-clip ground-truth/prediction CSV built for §8's leakage investigation, and `results/nemotron_maes8_hyps/*.tsv` (8 files, ref/hyp transcript dumps from an earlier local-only commit, `cd9bbdd`, predating this week's own work). Both are raw dysarthric/ALS patient utterance data, not code or aggregate results.

Since **none of the ~22 commits ahead of `origin` had ever been pushed**, rewriting local history was safe (no shared/collaborator history at risk). Stripped `results/nemotron_maes8_hyps/` from every commit in range via `git filter-branch --index-filter` (non-interactive, no `-i` flag), amended the sensitive CSV out of the commit that introduced it, and verified with `git diff --stat origin/realtime-port..HEAD -- '*.csv' '*.tsv'` coming back empty before allowing another push attempt. The classifier blocked one further push attempt with no reason given (possibly extra caution right after a history rewrite) — rather than retry against a security denial, left it for manual push. **Push subsequently succeeded** (confirmed via `git fetch` + `git ls-tree` on `origin/realtime-port`: the sanitized history is what landed, zero trace of the stripped files). The CSV itself was kept as a local-only, untracked file (`results/splitv1_merged_seed1_test40_breakdown.csv`) — useful for the analysis in §8, not meant for the public repo.

**Lesson for future sessions**: check repo visibility before generating or committing any per-clip raw-transcript artifact (CSV/TSV dumps of `ref`/`hyp`/patient utterance text) — these are qualitatively different from the prose docs' illustrative example sentences and should default to staying local/untracked on a public repo unless explicitly cleared for publication.

- **Beam search for Whisper streaming is untried.** Nemotron's offline beam search (`maes`, width 8, from an earlier week) cut merged WER 31.72%→23.35% by recovering blank-collapse clips, but was never wired into the streaming decode path (architecturally awkward — beam wants to hold multiple hypotheses open before committing, which fights AlignAtt's whole "commit to safe partial output early" strategy). Whisper's SimulStreaming CLI exposes `--beams`/a beam decoder option; every streaming number in this file used greedy (`--beams 1`). Worth a small trial to see whether the same tradeoff (WER gain vs. latency cost from more hesitant commits) shows up.
